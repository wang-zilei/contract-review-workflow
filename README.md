# contract-review-workflow

给 Codex 用的一份合同功能核验 skill。它要解决的事情很简单，把合同里要求的能力，和实际有没有覆盖，分开讲清楚。

## 什么场景用它

这里我直接拿一个真实工作场景来说。

手上有一份几十页的合同，按三个交付周期拆开，每一期都列着一批功能点。旁边还有一份已经整理好的功能清单，和一个能打开的产品平台。

要做的动作差不多是这几样。

1. 从 PDF 里把每一期要交付的功能抠出来，准确到原文和技术参数
2. 把这份功能和现有功能清单逐条对上，看哪些已经有，哪些还缺，哪些范围不一致
3. 打开产品，从总入口出发，把关键页面、表单、状态、权限和异常情况看一遍
4. 收尾时只把确实有差异的地方写成风险报告，附上合同页码和页面路径

再细化一点，这几种任务都能用到它。

- 合同 PDF 太大，需要按交付期或批次拆分再逐一核验
- 已经有 Excel 功能清单，但要回头检查 OCR 和视觉识别有没有错
- 要把合同要求和现有功能清单、PRD 或产品能力做对照
- 要用浏览器走查真实系统，但不能把没测到的页面直接算成风险
- 要把结果写进在线表格或文档，还得避免乱改表头和结构

如果只有一份合同，没有对照基线，这个 skill 不会硬猜覆盖情况，会先给你一份经过核验的合同功能清单，或者问你补一个对照对象。

## 它好在哪

一是三条证据链分开。合同原文、基线对照、页面观察各算各的，不会混成一种结论。

二是页面没点完，不等于合同有风险。菜单名字像，也不等于能力已经覆盖。

三是 PDF 始终是权威。已有的 Excel 只当一次提取结果回查，不能反过来盖过合同原文。

四是至少两遍核验。一遍看结构、分页、边界和重复，一遍看文字、数字、单位、数量和 OCR 容易错的地方。

五是必须有一个对照组才判断覆盖。没有对照对象，它不上来就下风险结论。

六是尊重你现有的表头和结构。你删掉的字段不会偷偷加回来，也不会为了好看塞一堆新列。

七是写完一定回读。写外部文档和表格之后，会再看一眼真实内容、行数、表头和残留，不会拿一个成功的 API 响应就宣布完事。

## 怎么运作

Step 1 先把合同来源定死。PDF 是权威，其他表格和识别结果都回到 PDF 核对。

Step 2 大合同先拆。按交付周期、批次、产品或章节分成小块，同时保留原 PDF 页码映射，跨页的表不会从中间切断。

Step 3 逐条提取功能。一行一个功能点，合同原文不改写，模糊的位置先标待确认，不猜。

Step 4 两轮核验。第一轮盯结构和分页，第二轮盯内容原文，把差异写进错误记录。

Step 5 定对照组。可以是一份现有功能清单、PRD、规格文档，也可以是浏览器能看到的真实产品能力。语义对照，不靠「列表」「编辑」「删除」这种词碰瓷。

Step 6 需要走查产品时，从你给的总入口开始，先看清可达模块，再进具体页面。只读优先，不随便提交真实任务和付费操作。

Step 7 分开输出。合同对照结论和页面核验状态分开记录，谁都别顶替谁。

Step 8 出报告。风险报告默认只放有明确差异的条目，保留合同页码、基线位置、实际看到和页面路径。复杂度和疑似过时判断仅在用户要求时做。

Step 9 写外层资源要回读。写入前读当前版本和表头，写入后核对结构、内容和残留。

就这样，一份合同该看什么、该对什么、该记什么，中间哪一步都不能省。
