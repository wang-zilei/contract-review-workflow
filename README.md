# Contract Review Workflow

事情是这样的。

一份合同 PDF 摆在面前，旁边还有功能清单、产品页面、测试环境和一堆看起来差不多的菜单名。你只想知道一件事，合同里答应交付的能力，到底有没有被覆盖。

然后最容易发生的事，就是把「名字像」当成「已经覆盖」，把「页面没测完」当成「合同有风险」，再把 OCR 识别出来的一串文字，当成合同原文直接交差。

一时间无语凝噎。。。

`contract-review-workflow` 是一个给 Codex 使用的合同功能核验 skill。它把合同原文提取、基线清单对照、线上产品验证拆成三条独立证据链，再把真正有依据的差异整理成可追溯的风险结论。

不是帮你把表格填满。

是帮你少下几个没有证据的结论。

## 它解决什么问题

很多朋友可能遇到过这种场景。

合同里写了几十页甚至几百页功能要求，项目已经有一份功能清单，线上还有一个能点开的系统。几份材料互相套着看，越看越像，越看越容易乱。

这个 skill 会强制把三件事分开。

1. 合同提取，忠实记录权威 PDF 到底写了什么
2. 基线对照，判断指定功能清单或规格文档是否覆盖合同要求
3. 产品核验，记录真实页面、接口或测试环境里实际观察到了什么

这三类结论不会互相顶替。页面没打开，不会自动变成合同风险。菜单名字相似，也不会自动算覆盖。

我是真的觉得，这个区分挺重要的。

因为合同核验里最危险的，往往不是漏看一个按钮，而是把「没看见」写成「不存在」。

## 适合什么时候用

- 从合同 PDF 中拆解可交付的功能点
- 复核已有 Excel 功能清单是否忠实对应合同原文
- 将合同要求与现有功能清单、PRD 或产品能力做语义对照
- 在真实产品中核验列表、表单、详情、状态、权限和异常路径
- 输出带合同页码、基线位置和产品证据的风险报告
- 对外写入文档或表格前后做结构与内容回读校验

如果你只有一份合同，却没有任何对照基线，这个 skill 不会硬猜覆盖情况。它会先产出经过核验的合同功能清单，或者请你补充比较对象。

克制。

有时候比聪明更重要。

## 安装

把仓库克隆到 Codex 的 skills 目录。

```bash
git clone <你的仓库地址> ~/.codex/skills/contract-review-workflow
```

重新打开 Codex 后，就可以在任务中直接调用。

```text
使用 $contract-review-workflow 审核这份合同 PDF，和现有功能清单做对照，只输出有明确差异的风险项，并保留合同页码和清单位置。
```

也可以让它继续核验真实产品。

```text
使用 $contract-review-workflow，从我提供的系统首页开始核验指定阶段的合同功能。合同、功能清单和页面观察分别给结论，不要把未测试页面直接标成风险。
```

## 它是怎么工作的

整个流程看着不复杂，但每一步都故意留了一道保险。

合同 PDF 是权威来源。已有 Excel 只是一次提取结果，需要回到原始页面复核。

遇到大合同，会按交付阶段、批次、产品或章节拆分，但不会从跨页表格中间把一条需求劈成两半。拆完以后保留原 PDF 页码映射，后面的每个判断都能找回出处。

提取结果会做两遍检查。一遍盯结构、分页、边界、漏项和重复项。一遍盯文字、数字、单位、数量、缩写和 OCR 容易认错的字符。

然后才开始对照。

对照时不靠关键词碰瓷。它会检查业务对象、模块层级、角色权限、动作集合、输入参数、输出状态、范围数量、集成关系和异常边界。只有名字像，没有用。

产品核验也一样。会从用户给定的入口开始，先看清可达模块，再检查列表、创建、详情、状态、权限和异常页面。观察事实单独记录，不会反过来污染已经成立的合同或基线结论。

证据成立后才会标风险。写入外部文档或表格后，还会重新读取目标，核对标题、表头、行数、排序、关键记录和残留内容。

成功返回一个 API 响应，不算完成。

真正写对了，才算。

## 判断原则

这个 skill 对风险结论比较较真。

以下差异通常可以构成风险依据，包括业务对象或用户角色不同、能力范围更窄、缺少合同点名的操作或生命周期状态、关键参数与数量不一致、集成依赖不同，以及证据直接和合同要求冲突。

但页面没点开、测试数据为空、菜单路径不同、界面看不到后端实现，这些都不能单独证明合同风险。

怎么说呢，合同审查不是大家来找茬。它更像一条证据链，链条中间断了，就老老实实标成待确认。

别硬接。

## 输出可以长什么样

输出结构优先沿用你已有的表头，不会自作主张把删掉的字段加回来。

当目标是一份风险报告时，建议至少保留这些信息。

| 信息 | 用途 |
| --- | --- |
| 合同原文 | 说明权威要求 |
| 合同页码 | 回到 PDF 复核 |
| 基线位置 | 找到对应清单或规格条目 |
| 产品观察 | 记录真实看到或执行的结果 |
| 差异与风险 | 说明对象、范围、参数或流程哪里不同 |
| 待确认项 | 保存证据还不够的问题 |

如果用户已有固定模板，就以用户模板为准。

## 仓库结构

```text
contract-review-workflow/
├── SKILL.md
├── README.md
├── agents/
│   └── openai.yaml
└── references/
    ├── workflow.md
    ├── judgment-rules.md
    ├── verification-checklist.md
    └── external-write.md
```

`SKILL.md` 定义能力边界和默认规则。

`references/workflow.md` 负责端到端流程和阶段选择。

`references/judgment-rules.md` 负责覆盖、风险、复杂度和疑似过时判断。

`references/verification-checklist.md` 是交付前的核验清单。

`references/external-write.md` 约束云文档和在线表格的写入与回读。

## 安全边界

默认优先只读检查。

浏览产品时，不会在没有授权的情况下提交真实任务、执行付费操作、删除数据或把密钥写进交付物。修改外部文档和表格前，会重新读取当前版本与结构，只改用户授权的范围。

说真的，越是合同这种东西，越不该靠胆子大。

证据要硬，动作要稳，没确认的就明确写没确认。

这就是这个 skill 想守住的东西。
